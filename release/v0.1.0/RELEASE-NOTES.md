# FileTools v0.1.0

本地部署的文件格式转换工具。所有转换都在你自己的机器上跑，文件不上传、不出内网。

## 这个版本装了哪些平台

| 平台 | 这一版给了什么 | 怎么装 | 真实状态 |
| --- | --- | --- | --- |
| Web | 静态站点（`FileTools-Web-0.1.0.zip`） | 解压后**挂在服务器根路径**（见下方说明）；或直接由后端 `frontend/dist` 托管 | 产物本身已验（见下），**未部署到真实服务器** |
| Windows | NSIS 安装包（`FileTools-Setup-x64.exe`）×64 位 | 双击装，装到当前用户目录、免 UAC | 安装 → 启动 → 卸载已实测；**桌面端「转换 + 结果落盘」未在真实窗口里验完** |
| Android | APK（`FileTools-0.1.0-release.apk`） | 侧载安装，需在系统设置里允许「安装未知来源应用」 | 能装、能打开，**但一个转换都做不了**（见下） |
| iOS | **这一版没有** | 见下方「已知限制」 | 无运行时验证 |

**Web 那份要挂在服务器根路径。** 打包时用的是站点根（产物里的引用形如 `/assets/…`，
不是 `./assets/…`），所以解压后要放到服务器的根目录、或配一条把 `/` 指过去的规则；
放在子目录（比如 `https://example.com/filetools/`）会**白屏**，因为浏览器会去
`https://example.com/assets/…` 找那些文件。
（桌面版走的是另一条构建路径，产物里的引用是相对的，和这一份互不影响。）

**Web 那份没有部署到过真实服务器。** 验的是「这份 zip 本身可独立部署」：
zip 是确定性的（同一份 `frontend/dist` 打两次逐字节相同），`index.html` 引用的每个本地
文件都在包里，同一套代码在真实浏览器里跑过 2,074 项断言。**但把它放到一台真实服务器上
并提供给真实用户访问，这一条没做过。**

## Android 那一份到底出了什么问题

**结论：这份 APK 装得上、打得开、界面全正常，但每一个请求都会被系统挡掉，
一次转换也完不成。**

两个各自独立的原因，任一个都足以让 App 不可用：

1. **系统的网络安全策略不允许明文 HTTP。** 这份包的 `targetSdkVersion` 是 **36**，
   而 Android 对 API 28+ 的默认策略就是**拒绝明文 HTTP**；本项目的后端只有明文 HTTP。
   已实测这份 APK 的清单里**既没有** `android:usesCleartextTraffic`、
   **也没有** `android:networkSecurityConfig`，包里**不存在**
   `res/xml/network_security_config.xml` 这个资源 —— 也就是说系统按默认策略办，
   请求在建立连接之前就被拒了。App 只能笼统地显示一句「无法连接服务器」。
   （为什么发布时没发现：Expo 的 prebuild 模板**只把** `usesCleartextTraffic="true"`
   写进 debug 变体的清单，release 变体的清单里没有；而当时的移动端验收是在 **Expo Go**
   里跑的，Expo Go 宿主 App 自己的清单是开着明文的，所以一路绿灯。）
2. **地址是打包时烤死的，装到设备上改不了。** 这份包用的是构建时的
   `EXPO_PUBLIC_API_BASE_URL`（当时是 `http://127.0.0.1:8011`），
   已实测它作为**字面量**躺在包的 JS bundle 里，而且 App 里**没有任何**改地址的入口。
   即便策略问题不存在，手机上的 `127.0.0.1` 指的也是**手机自己**，
   用户没有任何办法把它指到自己的后端上。

**怎么绕过（如果你现在就要用这份 0.1.0 的 APK）**：只能用 `adb reverse` 把设备端的
8011 端口转发到跑后端的机器上（`adb reverse tcp:8011 tcp:8011`），
并且后端必须跑在同一台通过 USB 连着设备的机器上 —— 而这仍然绕不过第 1 条。
**所以实际结论是：请改用 0.1.1。**

## 用之前要知道的

- **Web 版和 Windows 桌面版都需要后端在 `127.0.0.1:8000`。** 桌面版的地址是**构建时烤进去的**，
  换服务器得重新构建。后端怎么起见仓库 README。
- **Android 版（0.1.0）不可用**，原因见上一节。0.1.1 起地址可以在 App 的
  「我的 → 服务器」里改，并且明文 HTTP 的主机由打包时的配置决定。

## 已知限制（如实列出，不藏）

1. **Android 那份 APK 是 debug keystore 签名的。** 它能安装，但**不能上架应用商店**。
   这一版把它当「可侧载的测试包」发，不当正式商店包。正式签名需要一份 release keystore，
   而 keystore 属于你的私钥、不该由构建流程生成后随便躺着。
2. **Android 那份 APK 在真机上的行为没有被独立验收过。** 当时的原生路径验收是在
   一台 Android 15 / x86_64 的模拟器（AVD）上做的，而且走的是 Expo Go 那条路，
   不是这份安装包本身。**没有物理设备上的验收记录。**
3. **iOS 没有任何产物，也没有任何运行时验证。** 构建机上没有 macOS，一行都编不了。
   配置与图标资产是齐的（1024 图标已量过像素、无 alpha 通道），
   在一台 Mac 上跑一次 `expo prebuild` + Xcode 就能接上 —— 但**「配置存在」不等于「跑过」**。
4. **没有 Docker 镜像，也没有 Windows ARM64 产物。** 构建机上没有 docker；
   `rustup` 只装了 `x86_64-pc-windows-msvc` 这一个 target。与其发一个没验过的 ARM 包，不如不发。
5. **Windows 桌面版的「转换 + 结果落盘」未在真实桌面窗口里走完一次。**
   安装 → 启动 → 卸载这条流程实测通过，但「在真实窗口里完成一次转换并把结果存到磁盘」
   缺证据，所以这一项记为**待验证**，不记为通过。
6. **Windows 桌面版未启用 CSP**（`csp: null`）。原因是本版用 WebView2 的远程调试端口
   实测打不开，CSP 只验到一半，与其开一个验不全的策略不如先不开，等能验了再开。
7. **Windows 桌面版的拖拽只在文件选择区内生效**，不是窗口任意位置。
8. **Android 版上传非 ASCII 文件名，结果文件名会变成一串十六进制。**
   选「中文样张.jpg」转出来的结果叫 `E4_B8_AD_E6_96_87_E6_A0_B7_E5_BC_A0.png` ——
   **文件内容是好的**（字节、尺寸、像素都对），**只有名字是乱的**。根因在 `expo/fetch`
   拼 multipart 时对文件名做了 `encodeURIComponent`
   （`node_modules/expo/src/winter/fetch/convertFormData.ts` 的 `encodeFilename`），
   服务端再把 `%` 换成 `_`。**Web 端不受影响**（浏览器发的是原始 UTF-8，服务端实测能正确接住）。
   这一条是 0.1.1 的 Android 设备验收时才抓到的，写在这里是因为它同样存在于 0.1.0。
   **它已经在 0.1.1 里修掉了**（客户端显式声明、服务端才解码），请在 0.1.1 的说明里看细节；
   本目录这份 0.1.0 的产物**没有重打**，0.1.0 的 APK 仍然带着这个问题。

## 校验下载的文件

每个产物旁边都有 `SHA256SUMS.txt`。在下载目录里跑：

```bash
sha256sum -c SHA256SUMS.txt
```

Windows PowerShell 里：

```powershell
Get-FileHash .\FileTools-Setup-x64.exe -Algorithm SHA256
```

逐个和 `SHA256SUMS.txt` 里的值对。对不上就别装。
