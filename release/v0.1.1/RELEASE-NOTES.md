# FileTools v0.1.1

本地部署的文件格式转换工具。所有转换都在你自己的机器上跑，文件不上传、不出内网。

**这一版是为了修 0.1.0 的 Android 发行事故而发的。** 0.1.0 那份 APK 装得上、打得开、
界面全正常，但**一次转换也完不成**，而且装到设备上**没有任何办法把地址指到自己的后端**。
0.1.1 把这两条都修了。此外它还修掉了四处**从 0.1.0 起就存在**的缺陷 —— 三处下载交互、
一处中文文件名（见下面各节）。全部验收都跑在**要发出去的那份安装包**上（不是 Expo Go）。
0.1.0 的产物文件与校验和**一个字节都没动**，那份说明也原地保留、另加了一份纠正说明。

> 这一版**没有**改转换引擎、队列或核心 API —— 改的只有 Android 客户端的网络配置、
> 地址来源与文件名编码，加上客户端的三处下载交互，以及验证脚本。Web/Windows 的后端配置
> 一个字没动。

## 这个版本装了哪些平台

| 平台 | 这一版给了什么 | 怎么装 | 真实状态 |
| --- | --- | --- | --- |
| Web | 静态站点（`FileTools-Web-0.1.1.zip`） | 解压后**挂在服务器根路径**（见下）；或由后端 `frontend/dist` 托管 | 产物本身已验，**未部署到真实服务器** |
| Windows | NSIS 安装包（`FileTools-Setup-x64.exe`）×64 位 | 双击装，装到当前用户目录、免 UAC | 安装 → 启动 → 卸载已实测；**桌面端「下载到磁盘」未在真实窗口里验完** |
| Android | APK（`FileTools-0.1.1-release.apk`） | 侧载安装，需允许「安装未知来源应用」 | **安装包本身已在 AVD 上跑通完整链路**：装 → 启动 → 连上后端 → JPG→PNG → DOCX→PDF → 下载落盘 → 坏文件报错与重试；**没有物理设备**，见「已知限制」 |
| iOS | **这一版没有** | 见「已知限制」 | 无运行时验证 |

**Web 那份要挂在服务器根路径。** 打包时用的是站点根（产物里的引用形如 `/assets/…`），
放在子目录会白屏。

**Web 那份没有部署到过真实服务器。** 验的是「这份 zip 本身可独立部署」：zip 是确定性的、
`index.html` 引用的每个本地文件都在包里，同一套代码在真实浏览器里跑过 2,074 项断言。
**但把它放到一台真实服务器上给真实用户访问，这一条没做过。**

## Android 这次到底改了什么

### 1. 明文 HTTP 被系统挡掉 → 用配置插件给出正确的安全边界

原来的做法是「什么都不配」，而 `targetSdkVersion` 是 36，Android 对 API 28+ 的默认策略
就是**拒绝明文 HTTP**，于是所有请求在建立连接前就被拒了。

现在由 `mobile/plugins/withAndroidNetworkSecurity.js` 在 prebuild 时生成策略
（`mobile/android/` 是 prebuild 的产物且被 gitignore，改它不作数）：

| 变体 | 策略 |
| --- | --- |
| **release** | `base-config cleartextTrafficPermitted="false"`（默认全拒）+ 一份**白名单**：`10.0.2.2`、`127.0.0.1`、`localhost` |
| debug / debugOptimized | 明文全开，与 Expo 模板原行为一致，只影响开发变体 |

**没有全局放开明文。** 白名单里那三个是「本机 / 模拟器宿主」的地址；
要让设备连别的明文 HTTP 服务器，得在打包时用 `FILETOOLS_ANDROID_CLEARTEXT_HOSTS`
显式加进去（见 `mobile/.env.example`），**这是有意的**：安全边界不该为了跑通一个测试就拆掉。
生产环境请用 HTTPS —— 它不受这份白名单限制。

### 2. 地址烤死改不了 → 「我的 → 服务器」里可以改

原来地址是构建期的 `EXPO_PUBLIC_API_BASE_URL`，作为**字面量**躺在 JS bundle 里，
App 里没有任何改地址的入口。现在：

- 构建期的值降级成**出厂默认值**；
- 「我的」页可直接填一个新地址（`http://` / `https://` 都行，本地持久化，重启还在），
  也能一键恢复成安装包自带的那个；
- 改完会立刻重新拉一次后端能力，不用重启 App；
- 现在显示的地址**是**连接用的那一个，并且标出它是「安装包自带的默认值」还是你改过的。

> ⚠️ **出厂默认值 `http://127.0.0.1:8011` 是构建机上的开发地址，不是生产地址。**
> 手机上的 `127.0.0.1` 指的是**手机自己**。这一版**没有可用的生产 HTTPS 地址** ——
> 所以它把「填一个你自己的地址」做成了正经功能，而不是替你编一个地址。
> 请到「我的 → 服务器」里填你实际部署的后端地址。

### 3. 上传中文文件名，结果名会变成一串十六进制 → 已修

0.1.0 起就有：选「中文样张.jpg」转出来的结果叫
`E4_B8_AD_E6_96_87_E6_A0_B7_E5_BC_A0.png`。**文件内容完全正确**（字节、尺寸、像素都对），
**只有名字是乱的**。

根因不在我们这边，而在客户端与服务的**约定**上：Expo SDK 57 的原生 `fetch` 拼 multipart
时**无条件**把文件名过一遍 `encodeURIComponent`（`expo/src/winter/fetch/convertFormData.ts`
的 `encodeFilename`，没有开关可关），而服务端按字面收下 —— 那个 `%` 随后被文件名清洗规则
换成 `_`。于是同一个「中文样张.png」，Web 上传得到 `中文样张.jpg`，Android 上传得到
`E4_B8_AD…`。

修法是**客户端显式声明、服务端才解码**，不做任何猜测：

| 客户端 | 发的内容 | 声明 | 服务端做什么 |
| --- | --- | --- | --- |
| 浏览器 | 原始 UTF-8 | 不发 | 什么都不做 |
| 原生（本版起） | `encodeURIComponent` 过的 | 发 `filename_encoding=uri-component` | 解一次 |

**为什么不猜**：`a%20b.png` 既可能是「文件真的叫 `a%20b.png`」（浏览器发原文），也可能是
「文件叫 `a b.png`，被编码了」（原生发的）。服务端从字符串上看不出来，任何「看着像
percent-encoding 就解一下」的启发式都会**解错前者**。所以解码只由发起编码的那一端触发。

⚠️ **残留风险，如实记下**：将来 expo 若改发原始 UTF-8 却**仍然**发这个声明，那么一个字面
含 `%XX` 的名字会被多解一次。这个声明与「文件名已编码」这个事实绑在一起，两边必须一起改。

**Web 端不受影响**，走的是同一条「不声明就不解码」的路。后端新加的
`tests/test_filename_encoding.py` 把「原生端必须发、Web 端必须不发」钉死了，并且有一条
机械对账：扫全部路由，凡是收 `UploadFile` 的都必须挂上这个依赖（端点会越加越多，漏一个
就是一个静默的错名）。

## 顺带修掉的三个「下载」缺陷（非本次事故引入，0.1.0 就有）

这三个是这一轮跑长回归时**真点出来**的，不是顺手重构。

`download_url` 是**一次性令牌**：服务端发完文件就把结果删掉、令牌同时作废。**移动端**原来只在
单项卡片上记了「已保存到本机」，**没有跟着看服务端**，于是留下两个点了就 404 的按钮：

1. **结果已经被取走之后重新打开任务页，单项卡片上还挂着一个可点的「下载」。**
   服务端在结果被取走时只把**整批**的 `download_url` 置空、`expired` 置真，单项那个字段
   原样留着；移动端只看单项字段，于是按钮还在。真点过：HTTP 404 + 「下载链接无效或已过期」。
   这正是长回归里那条红背后的真缺陷 —— 它原来被一个抢跑的等待条件挡着（断言在快照到位
   之前 44 毫秒就跑了），**假红底下压着一个真缺陷**。
2. **只有一份结果的批次里，下走那一份之后「打包下载」不会消失。**
   这种批次里整包地址与单项地址是**同一个令牌**（2026-10-11 直接打服务端量过：
   两个 `download_url` 逐字相同；下走之后整批那个变 `null`、`expired` 变真，再取一次是 404），
   所以这一份被取走，整包那个也跟着作废。再点一下是个**连提示都没有**的死按钮 ——
   整包这条路径的 `.catch` 是空的，用户看到的就是「点了没反应」。
3. **整包「打包下载」失败时，界面上一个字都没有。** 这一条就是上面第 2 点末尾提到的那个
   空 `.catch`：写它的时候「全部结果」这张卡还不存在，注释里写着「弹一句失败也无处安放」。
   卡片后来有了，那个空 catch 就变成了**点了没反应** —— 地址真作废时下面那句「已过期」
   还能兜住，但网络断了、ZIP 没打出来、服务端 500 这些情况快照一个字都不会变，
   屏幕上什么都不会发生。

   现在失败会**画在「全部结果」那张卡里**，措辞走和单项下载失败**同一条口径**
   （`explainError`：只认错误码 + 服务端给的人话），异常对象自己的 `message`
   （`TypeError: …`、`Failed to fetch`）永远不上屏，堆栈更不会。**没有另起一套 toast** ——
   用的是页面已有的 `Notice`，和单项卡片上那句失败提示是同一个组件。

   为什么只画在卡片里、不做页面级提示：这条消息和卡片下面那句「结果已经被下载过或已过期」
   是**互斥**的 —— 真过期时重拉的快照会把地址撤下，卡片连同这条提示一起消失，由那句话接管。
   挂到页面级就会两条消息同时站着、还互相打架。

   顺带堵掉一个自己造的红：地址是一次性令牌，连点两下时先回来的那个会把令牌用掉、
   后一个变成 404，**下载明明成功屏幕上却多一句失败** —— 所以按钮在下载期间转圈并挡住
   第二次点击（就是下面表里的「打包中…」）。

前两处都改成「听服务端的」：单项按钮按整批快照的 `expired` 收起来；下载完（单项或整包）
重拉一次快照。第三处给失败找了地方安放。长回归里这几条都补了新断言钉死，并在
**要发出去的那份 APK** 上整轮复验过（见下表）。

**没有为了跑通而放宽任何断言**：这两条是新加的，原有断言一条没删、没弱化。

## 用之前要知道的

- **Web 版和 Windows 桌面版都需要后端在 `127.0.0.1:8000`。** 桌面版的地址是**构建时烤进去的**，
  换服务器得重新构建。后端怎么起见仓库 README。
- **Android 版的地址可以在「我的 → 服务器」里改**，出厂默认值只是构建机上的开发地址。
- **明文 HTTP 只有白名单里那三个主机能用**（`10.0.2.2` / `127.0.0.1` / `localhost`）。
  其余一律要 HTTPS，或者打包时显式加白名单。

## 已知限制（如实列出，不藏）

1. **中文文件名的修法是「客户端声明、服务端才解码」，两边必须一起改。**
   本版之后 Android 上传的中文名是对的（上表 A 段已验，屏幕上和磁盘上都是中文）。
   但那个声明（`filename_encoding=uri-component`）与「文件名已被
   `encodeURIComponent`」这个事实绑在一起：将来 expo 若改发原始 UTF-8 却**仍然**发这个
   声明，一个字面含 `%XX` 的名字会被多解一次。**改这里就得同时改客户端。**
   后端 `tests/test_filename_encoding.py` 把「原生端必须发、Web 端必须不发」钉死了。
2. **Android 那份 APK 是 debug keystore 签名的。** 能安装，**不能上架应用商店**。
   正式签名需要一份 release keystore，而 keystore 是私钥，不该由构建流程生成后随便躺着。
3. **Android 没有物理设备上的验收记录。** 上面那张表全部产自一台 AVD（Android 15 / x86_64）。
   模拟器与真机在 SAF 选择器、权限、厂商 ROM 上都可能不一样。
4. **iOS 没有任何产物，也没有任何运行时验证。** 构建机上没有 macOS，一行都编不了。
   配置与图标资产是齐的（1024 图标已量过像素、无 alpha 通道），但
   **「配置存在」不等于「跑过」**。
5. **没有 Docker 镜像，也没有 Windows ARM64 产物。** 构建机上没有 docker；
   `rustup` 只装了 `x86_64-pc-windows-msvc`。
6. **Windows 桌面版的「下载到磁盘」未在真实桌面窗口里走完一次。**
   安装 → 启动 → 卸载实测通过；后端联通已实测；落盘那三条防线（中文名 / 路径穿越 / 重名）
   有 13 条 Rust 单元测试打在生产函数上并已跑过。但**「在真实窗口里点一次下载、看文件
   真的落到下载目录」缺证据** —— 取证要开 WebView2 的远程调试端口，而那个端口在本机
   开不出来（见 README 的已知限制），所以记为**待验证**，不记为通过。
7. **Windows 桌面版未启用 CSP**（`csp: null`），原因同上：远程调试端口打不开，
   CSP 只验到一半，与其开一个验不全的策略不如先不开。
8. **Windows 桌面版的拖拽只在文件选择区内生效**，不是窗口任意位置。
9. **`versionCode` 仍是 `1`**（与 0.1.0 相同）。侧载升级不受影响；真要上架时得把它加一。
10. **「打包下载」失败的提示：修了，但两条验证路径的深度不一样。**
    整包这条路径原来是空 `.catch`，用户只会看到「点了没反应」；本版给失败在
    「全部结果」那张卡里安了地方（措辞与单项失败同一条口径，不露异常与堆栈）。
    验证深度如实分开写：

    - **浏览器里验得最深**：长回归的 C4 段真开界面提交一批两个文件，
      成功一次、**注入服务端 500 一次、注入连不上一次**，两次失败都断言了「提示画在卡里」
      且「按钮回到可点状态、没卡在『打包中…』」，最后**再真下一次**确认还能下（见 §八 回归读数）。
    - **要发出去的那份 APK 上只验了主线**：下载成功 → 按钮自己收起 → 界面翻成
      「已经被下载过或已过期」（上表 6b）。**设备端没有造过「打包过程中失败」**，
      所以「失败提示在手机上长什么样」这一条在设备上是**没验过的**，不写成通过。
11. **在 Windows 上检出仓库，`SHA256SUMS.txt` 会变成 CRLF，`sha256sum -c` 跑不通
    （哈希本身一个字都没错，错的是换行）。** 这一条**已经在根上修了**，说明如下。
    实测：CRLF 那份 exit 1、三条全是「No such file or directory」；LF 那份 exit 0。
    两个成因，**不在同一层**，都得修：

    - **生成端**：`scripts/build_release.py` 写文件时没指定换行，Windows 上默认带 `\r`。
      已改成显式 `newline="\n"`，并在 `verify_release.py` 里加了一条**读原始字节**的断言
      钉死（原来那几条断言用 `splitlines()` 读，会把 `\r` 吃掉，看不出这个毛病）。
    - **检出端**：`.gitattributes` 里原本只有 `* text=auto`，而开发机开着
      `core.autocrlf=true` —— 于是**索引里存的明明是 LF**，在 Windows 上检出到工作区就成了
      CRLF（实测：`i/lf w/crlf`，blob 294 字节 / 工作区 297 字节，差的正是 3 个 `\r`）。
      `.gitattributes` 已补一条 `SHA256SUMS.txt text eol=lf`，与仓库里既有的
      `*.sh` / `.nvmrc` 是同一种做法。

    **0.1.0 已发布的那份内容没有动**：仓库里存的 blob 本来就是 LF，上面那条规则只影响
    「检出成什么」，不改任何已提交的内容（实测 `git add --renormalize` 对这些文件零 diff，
    0.1.0 目录下也没有任何文件被判成改动）。唯一还会看到 CRLF 的地方是本机那份**旧的工作区
    副本** —— 删掉重新检出即可，命令是
    `git checkout -- release/v0.1.0/SHA256SUMS.txt`，**没有替你执行**。

## 校验下载的文件

每个产物旁边都有 `SHA256SUMS.txt`。在下载目录里跑：

```bash
sha256sum -c SHA256SUMS.txt
```

这一版的 `SHA256SUMS.txt` 是 **LF 换行**，上面那条命令在本机实测 **exit 0、三条全 `OK`**。
（0.1.0 那一份是 CRLF，同一条命令会失败 —— 见「已知限制」第 11 条。）

Windows PowerShell 里：

```powershell
Get-FileHash .\FileTools-Setup-x64.exe -Algorithm SHA256
```

逐个和 `SHA256SUMS.txt` 里的值对。对不上就别装。
